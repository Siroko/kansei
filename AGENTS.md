# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

## Where work happens

- Active development is the Rust engine in `rust/` (workspace: `kansei-core`, `kansei-wasm`, `kansei-native`); the TypeScript library in `src/` is the older port. Open PRs against `development`, not `main`.
- kansei.graphics is a Vercel production build of `main`: `pnpm bundle-examples` on Node 24.x, which the Vercel project's Node.js Version setting picks (package.json has no `engines`, so npm users of the package get no engine warning; `.nvmrc` and `devEngines` cover local work), output `dist/`. The landing page is `site/` (copied to the dist root) and the curated list is `examples/index.html`; `development` reaches the site only when merged into `main`. The Rust examples and demos are served at `/examples/<name>/` from the `site-wasm` branch, which `.github/workflows/site-wasm.yml` builds on pushes to `main` (`scripts/build-wasm-examples.sh`, which says what it leaves out); the Vercel build only copies it in, so a page must load everything by relative URL (the build rewrites its `../pkg/` import). `pnpm dev` stands in for that layout (`scripts/vite-dev-site.ts`): `site/` at the root and a local `scripts/build-wasm-examples.sh` output (or `WASM_EXAMPLES_DIR`) at `/examples/<name>/`; without one, `examples/index.html` sends its Rust links to kansei.graphics. List a new example there as a row under its area, with a TS and/or WASM button (a TS page and its Rust twin share one row; parameter variants and sibling pages are dashed buttons on it); test and regression pages stay off the list, named in its comment, and rows the owner curated off keep their markup as `<li hidden>` (an emptied area is hidden with its nav link). `fluid.kansei.graphics` (Vercel project `kansei-fluid`, root `rust/kansei-wasm/examples/fluid/`) builds nothing: its `vercel.json` proxies `kansei.graphics/examples/fluid/`.
- Two tiers of standalone crates, each with its own `[workspace]` and listed under `exclude` in `rust/Cargo.toml` (names are unique across both): `rust/kansei-wasm/examples/*` each teach one engine feature, and `rust/kansei-wasm/demos/*` are showcases (lake, motion-matching, voxel-gi-particles, fluid_clock, steering_text, joydivision) that may carry art-directed WGSL and their own logic, their READMEs naming what is demo-local. Build one with `wasm-pack build --target web --release` in its directory, serve that directory, and open `www/`. Their web plumbing (canvas sized by CSS box and device pixel ratio, resize, frame loop, query params, fetch) comes from `rust/kansei-wasm` (`Canvas`, `run`, `param`; `run` keeps at most two frames on the GPU, `?inflight=0/1/2`): don't copy it into an example. A page that starts its example with `launch` (from its pkg) instead of `start` also runs it in a Web Worker on an OffscreenCanvas with `?worker=1`, the same Rust unchanged (`kansei-wasm/src/worker.rs`, `js/`): its UI calls exports through the API `launch` returns (each a promise), and anything of `window` or `document` the example reads must go through kansei-wasm (`fluid` and `voxel-gi-particles` do). The TS examples (`examples/index_*.html`) get the same from `src/web` (`Canvas`, `run`, `paramOr`, `Keys`), imported as `../src/web/index` because `update-imports` maps `../src/<path>` to `dist/<path>.js`. Anything else a TS page imports must be plain `.js` beside it (nothing else is rewritten): a page and its Rust twin can share WGSL and generators from `examples/<name>/` (the crate `include_str!`s the `.wgsl`, the page fetches it), as `outdoor-gi` does; that example also fetches the Raggare intro's data and CC0 scans from raggare.kansei.graphics at run time, none of it in the repo. Examples and demos use kansei-core's public API only (`cargo test -p kansei-wasm` fails on an `include_str!` into kansei-core's files): what an example needs from a private shader becomes a public constant or stock material. Surfaces drawn through a `PostProcessingVolume` start from `Material::standard_lit` (scene lights and shadows, sky hemisphere, emission, instancing, velocity), `Material::emissive` and `Material::gradient_sky`; custom shaders compose `lights::LIGHTS_WGSL`, `shadows::SHADOW_MAP_WGSL` and `materials::GBUFFER_OUT_WGSL` instead of re-declaring those bindings. TS has the same (`Material.standardLit`, `emissive`, `gradientSky`; the chunks in `src/materials/shaders/SharedWGSL.ts`), the renderer packing the scene's lights into every camera's group 1 binding 2.
- The npm package `kansei` is the TS engine's `dist/` (`pnpm build`, run by `npm pack`/`publish` through `prepack`; `CHANGELOG.md` per release). The site loads those same files without a bundler, so dist must stay self-contained: gl-matrix stays bundled (a dependency only for the declarations' types), and assets are inlined as plain strings (`?url`, not `new URL(..., import.meta.url)`, which Vite's dev server rewrites in a consumer's pre-bundled deps). Check a release by installing the packed tarball in a project outside the repo and running it under both `vite` and `vite build`.
- Textures ship as KTX2 (Basis Universal), transcoded per device by `loaders::ktx2` (TS: `src/loaders/KTX2Loader.ts`, over Binomial's prebuilt transcoder wasm, which differs from Rust's in two build flags); encode with `rust/tools/ktx2` (needs `basisu`). See `docs/ktx2.md`. The transcoder crate is vendored and trimmed in `rust/vendor/basisu` (`PATCHES.md`): a new target needs its dispatch arm back.

## Verifying

- `cargo test -p kansei-core` validates every WGSL module with naga and checks each `#[repr(C)]` uniform struct against its WGSL size (see the `shaders_validate_*` tests); keep that pattern for new shaders. Chrome rejects some WGSL naga accepts (reserved words such as `patch` as names; `f(a < b, c > d)` read as a template list, so parenthesize the comparisons): load a new shader in the browser too.
- `rust/kansei-core/tests/*_gpu.rs` run shaders on a real adapter and read results back; they pass without running when no adapter exists.
- `pnpm test` runs the TS engine's CPU-only tests (`tests/**/*.test.ts`: Rust `#[test]`s ported one for one) in Node through Vite (`scripts/run-tests.mjs`); `tsc` type-checks them with `src`.
- Headless browser checks: run `chrome-devtools-axi` with its own `CHROME_DEVTOOLS_AXI_SESSION` and `CHROME_DEVTOOLS_AXI_CHROME_ARGS="--enable-unsafe-webgpu --enable-gpu --ignore-gpu-blocklist"`, and serve examples on a port nobody else uses, with `Cache-Control: no-store` (Chrome otherwise keeps the old `pkg/` from `python3 -m http.server` across rebuilds).
- GPU cost in the browser: wgpu 24's WebGPU backend does not implement `queue.on_submitted_work_done`. Add `--disable-gpu-vsync --disable-frame-rate-limit` to the Chrome args and time the interval between frames. For a breakdown, `Renderer::set_profiling(true)` then `take_profile().report()`: every labelled pass's GPU time (`profiling::gpu_pass` on new passes) and the frame's CPU sections; add `--enable-webgpu-developer-features` for unquantized timestamps. The TS engine has the same under Rust's pass labels (`Renderer.setProfiling`, `takeProfile`, `gpuPass` on new passes; `?profile=1` and `?bench=1` on pages wired to `examples/profile-hud.js`). Other sessions share this Mac's GPU, so separate runs differ by tens of percent: alternate A and B inside one page (the occlusion-culling example's `bench=1`). The profiler times a frame only while one of its 8 readbacks is free, so under load its timings arrive seconds late: after switching live, wait about 4 s before a profile window. On Apple GPUs consecutive passes overlap, so time a span across passes rather than each pass's own timestamps. Leave no animating WebGPU page open between captures (load `about:blank`). The Rust fluid example and `examples/index_fluid.html` take `?hud=1` (frame intervals in refreshes, sim steps) and the same `?n=`/`?bounds=` for side-by-side comparisons (`?match=ts&dpr=1` on the Rust one for the TS settings).

## Sharp edges

- The TS engine imports some WGSL straight from `rust/kansei-core/src` with Vite `?raw` (`grep -rn '?raw' src`: `src/materials/shaders/SharedWGSL.ts`, `src/gi/GiWGSL.ts`, `src/culling/InstanceCulling.ts` and others, under the Rust constant names; `assemble` in `ShaderUtils.ts` mirrors Rust's concat and `KANSEI_*` replace). Editing one of those files, or the bindings it declares, changes both engines: load the TS examples that include it too. A data layout such a shader reads changes in the TS packer too (`RtMesh.gpuWords` misread every vertex after the Rust grid's went to five words).
- `queue.write_buffer` lands before the next submit: several writes to one buffer inside a submit leave only the last one for every pass. Give per-dispatch parameters their own slots (or buffers).
- Each `queue.write_buffer` costs tens of microseconds in Chrome: upload a frame's data in one write, not one per dispatch or object (`culling::InstanceCulling` writes all its views once a frame, into one buffer its dispatches index).
- Depth is `[0, 1]` in both engines (`glam::Mat4::perspective_rh`; TS `Matrix4.perspective`/`ortho` use gl-matrix's `perspectiveZO`/`orthoZO`, never plain `mat4.perspective`), cleared to 1.0, so a depth of 1.0 means sky. Front faces are counter-clockwise and materials cull back faces by default.
- The GBuffer's four MRT targets fill WebGPU's default 32 bytes per sample (rgba8unorm counts 8), and wgpu 24's web backend cannot request more: another per-pixel output needs its own pass, as the velocity pass does. Both engines' volumes render it single-sample and anti-alias with `TemporalAAEffect` (TS pages that keep MSAA pass `PostProcessingVolume`'s `{ msaaSampleCount: 4 }`).
- Shadow, reflection and velocity passes redraw each material through its own `vertex_main`, with the light or mirror as the camera (see `Material::get_depth_pipeline`; in TS `Material.getDepthPipeline`, which `ShadowMap` draws casters with). Vertex shaders must not read group 3. Mark `@builtin(position) @invariant` where a second pass depth-tests against the GBuffer.
- Apple GPUs drop hidden opaque fragments whatever the draw order, but not fragments that write `@builtin(frag_depth)` (shaded before any depth test) or may `discard` (spared only by what was drawn before them): a pile of impostors shades most of its layers. Draw the quad at the sphere's nearest point (no frag_depth), and give costly shading a depth prepass and an equal-depth pass, both `@builtin(position) @invariant` (`voxel-gi-particles`' spheres). Alpha-tested foliage is the same: in `outdoor-gi` the cascades' shadow lookup on every layer of the spruces' cards cost about 10 of a 23 ms GBuffer pass at 1080p, and four comparison taps in place of the PCSS (`foliage_sun_shadow`) won back only 3. Moving opaque walls after the impostors measured slower.
- Group 3 (shadows and lights) only grows by additive bindings; `renderers/shared_layouts.rs` lists them (TS: `SharedLayouts.shadowBindGroupLayoutEntries`, the same 13). Both renderers render their shadow maps from lights with `cast_shadow`/`castShadow` once `enable_shadows`/`enableShadows` (and the point and spot variants) are on; TS maps bound through `Renderer.shadowMap`/`cubeMapShadowMap` are left to the caller. It is fragment-only: compute passes read the lights and shadow maps through `shadows/compute_shadows.rs` (group 0 bindings 1 and 3-9, shared by the volumetric fog and voxel GI's injection; TS: `src/shadows/ComputeShadows.ts`, whose `SHADOW_MAP` layer, an area light owning the 2D map, only the TS fog's injection honours).
- Voxel GI of meshes (`Renderer::enable_voxel_gi`, shown by `gi::VoxelGIEffect`; TS `Renderer.enableVoxelGI`, `Renderable.gi`, `MaterialOptions.voxelFragmentEntry`, `src/gi/VoxelGIEffect.ts`, without the distance field and probes yet) voxelizes only renderables with `Renderable::gi`, through their own `vertex_main`; varying albedo needs the material's `voxel_fragment_entry` (`gi::VOXEL_WRITE_WGSL`: group 3 bindings 100-102 in that pass). Static renderables are revoxelized only when transform, visibility or surface change: call `SceneVoxelGi::invalidate` after changing a texture. Behind thick walls with unlit outer faces the cones keep about 80% of the light (`tests/voxel_gi_scene_gpu.rs`); `rust/kansei-native/examples/gi_box_reference.rs` path-traces gi-box as the reference. Its distance field (`SceneVoxelGi::enable_sdf`, read with `gi::SDF_WGSL`) floods only the static seeds when they change and the dynamic ones every frame; on surfaces use `sdfSurfaceShadow`, not `sdfSoftShadow`, or a surface shadows itself at grazing angles. Its probes (`SceneVoxelGi::enable_probes`) trace that field and read the lit volume; `VoxelGIEffect::set_probes` swaps the per-pixel cones for them, and materials read them with `gi::PROBES_WGSL` (`kansei_gi_irradiance`).
- Voxel GI past a room is a clipmap round the camera (`Renderer::enable_voxel_clipmap`, shown by `gi::VoxelGIEffect::with_clipmap`): it revoxelizes only the slabs its windows move into, draws instanced renderables through cull views of its own (`InstanceCulling::with_gi_lod_range` picks the LOD they voxelize; cards keep their alpha test through `kansei_voxel_write_coverage`), and reads black until its sky is set (`SceneVoxelClipmap::use_sky_lighting`). Its probes (`enable_probes`) give materials sky visibility (`gi::CLIPMAP_PROBES_WGSL`) and the fog its ambient (`VolumetricFogEffect::set_clipmap_probes`); the `outdoor-gi` example uses them all.
- Ray tracing (`kansei_core::rt`): `Renderer::enable_rt_grid` keeps a grid of world triangles round the camera (or a fixed box) from the renderables with `Renderable::rt`, culled and cluster-cut for its box on the GPU; instanced ones need an `rt_placement` that does what their vertex stage does. Trace it from compute with `rt::RT_GRID_WGSL` (`RtGrid::bindings_wgsl`; the includer defines `kansei_rt_covered` for alpha tests) and give effects `SceneRtGrid::handle`, which follows its buffers when they grow. `RtReflectionsEffect` reflects only surfaces whose material returns `kansei_gbuffer_out_specular`: F0 lives in the GBuffer normal's alpha and roughness in the albedo's, so leave those alphas at 1 elsewhere. Glass (`StandardLitOptions::glass`/TS `glassOptions`, `kansei_gbuffer_out_glass`) marks itself by an albedo alpha of 0.05-0.45 (its roughness; 1 / IOR in the normal's alpha, the tint in the albedo) and is drawn by `RtReflectionsEffect::set_glass`; its renderable takes `RtSurface::glass`, a grid flag every trace passes through unless it asks for `KANSEI_RT_GLASS_HITS`, so GI and shadow rays see through glass. The reflections and glass need the voxel GI running whatever GI is on screen (`gi-box` shows all of it).
- Diffuse GI has three interchangeable paths on one scene setup: voxel cones (`gi::VoxelGIEffect`), screen space (`ScreenSpaceGIEffect`) and the hybrid `rt::RtDiffuseGiEffect` (rays through the RT grid, voxel GI for the hits' further bounces and past the grid, SVGF; closest to a path-traced reference, at a cost between). The hybrid needs the grid (`Renderer::enable_rt_grid`, `Renderable::rt` on what the rays should hit) and the voxel volume or clipmap, and `update_lights` each frame; its `RtGiMode::Reference` with `accumulate` is the ground truth to compare against (`docs/plans/2026-10-05-rt-grid-design.md` section 4). TS: `RtDiffuseGiEffect` (`src/rt`), on a single-sampled GBuffer: 4x MSAA resolves normals toward zero at edges, and SVGF spreads their NaN through its history.
- Instances culled on the CPU for the camera also drop out of shadow maps and reflections. Use `culling::InstanceCulling` (TS: `Renderable.instanceCulling`), which culls per view on the GPU.
- Cluster LOD (`Renderable::clusters`): each view draws its own cut, but impostor bakes and point-light (cubemap) shadows draw the renderable's geometry, which must be the mesh its graph was built from. The TS builder (`src/clusters`, with its optimesh port in `src/clusters/meshopt`) builds Rust's graph word for word because every f32 operation is wrapped in `Math.fround` (exact for + - * / sqrt): keep edits to it f32-exact, and regenerate `tests/fixtures` with `rust/tools/meshopt-fixture` when `clusters/build.rs`, `cards.rs` or the optimesh version change. JS `Math.sin`/`cos` round differently from Rust's `sinf`, so meshes generated with them match only to a last bit.
- Skinned materials (`animation::SKINNING_WGSL`) skin in their own `vertex_main`, but the single directional shadow map (`enable_shadows`) draws casters with a shared depth shader: a skinned mesh casts its bind pose there, so use cascaded shadows. The TS port (`src/animation`, `examples/index_skinning.html`, whose `?check=1` runs the ported Rust tests and the shader against `skinCpu`) still takes `kansei_sun_shadow` in its skinned lit shaders from the directional `ShadowMap` (which does draw skinned casters), not from `Renderer.enableCascadedShadows`.
- Never commit animation data, character meshes or anything derived from them (glTF exports, `.kmm` packs) unless their licence allows a public MIT repo: third-party sets such as Epic's GASP stay in a private folder, and the motion-matching demo (kept off the site; its `www/kimodo.html` plays the generated packs) loads packs from a local path (`rust/kansei-anim-bake/README.md`). The TS port's page (`examples/index_motion_matching.html`) reads them from the gitignored `examples/pack/`, and `bundle-examples` fails on any pack in `dist/` (`scripts/check-no-packs.sh`). Its world (course, lake, cannon, mill) is the pack-free `lake` demo's crate, which it depends on. Generated clips (`rust/kansei-anim-bake/genanim`, NVIDIA Kimodo in Docker on an NVIDIA PC) stay out of git too, and GASP is NoAI: no GASP pose, clip, render or the mannequin may go into a generator; they meet only at bake time. Music recordings never go in the repo or the site either (`.gitignore`, and `scripts/build-wasm-examples.sh` fails on audio): an example plays a file the viewer supplies, as `joydivision` does.
- `FluidMarchingCubes` draws voxel faces unless `set_use_classic(true)` (interpolated marching cubes). For a liquid's surface, `DensityFieldOptions::particle_radius` swaps the splatted density for a surface field (iso 1): spray stays droplet-sized and settled layers read flat. Walls, floors and moving colliders act on the fluid as `FluidSubstepPass`es run per substep (`update_batched_with`); the `lake` demo (`rust/kansei-wasm/demos/lake`) shows them. `FluidSimulationOptions::solver` picks SPH or Position Based Fluids (`simulations/fluid/pbf.rs`) on the same buffers, grid and substep passes. That grid is `simulations::grid::NeighbourGrid` (`FluidSimulation::grid`): other particle systems sort into one of their own, and passes that walk one bind its `params_buffer` with `NEIGHBOUR_GRID_WGSL`, not a copy. A fluid nobody sees or touches can rest: `FluidStepper::with_rest` (fixed steps at a `WorldScale`, over `FluidSleep` and `FluidSpeedProbe`), its state shown with `FluidSurfaceEffect::set_activity`, as the lake does; fill it at rest density with `PlanarContainerShape::lattice` or `fill_box` and `lattice_density`. The effect's surface goes into the scene as `FluidSurfaceEffect::surface_renderable`; step simulations with `pacing::FixedStep`, which takes at most a 60 Hz frame's time a frame (slower, the sim falls behind real time rather than piling on steps, which collapsed the frame rate). Fluid can be added at runtime: `FluidSimulation::with_capacity` reserves room, `emit`/`FluidNozzle` append into it (every pass runs on the live `particle_count`), `reset_particles` restores a fill; water squeezed between a collider and the container floor jitters and never sleeps, so keep colliders clear of the bed.
- Animation code (`animation/`, `collision/`) is clean-room: from papers and permissively licensed code, credited in the module docs. Never port Unreal Engine source (PoseSearch, AnimationWarping…) or GASP Blueprints; read what a clip needs from its tracks, not engine metadata. The TS port (`src/animation/motion_matching`, `src/collision`) plays the same clip and frame as Rust frame for frame on real packs: its search distances sum in f32 in glam's wasm (simd128) order, because mirrored frames of a cycle tie exactly and f64 breaks the ties differently.
