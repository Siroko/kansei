# SMAA in One Pass Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `SmaaEffect`, SMAA 1x in one compute dispatch with a three-pass reference behind the same type, a `smaa` example whose `?bench=1` shows the single pass cheaper than TAA and than the three passes at 1080p, the velocity pass skipped when nothing in the chain reads it, and film grain kept under SMAA.

**Architecture:** The SMAA algorithm (luma edges, orthogonal pattern search over SMAA's area texture, corner rounding, neighbourhood blending) is written once, in `shaders/smaa_common.wgsl`. It reads pixels through three accessor functions that each including module defines. The three-pass module reads textures. The single-pass module reads a 16 x 16 tile and its apron from workgroup memory. Both modes compute the same image, and the GPU test proves the fusing correct by comparing them. The renderer asks the chain `reads_velocity()` before it draws motion vectors. The tonemapper can leave grain and dither (moved into a shared `shaders/film_grain.wgsl`) to `SmaaEffect`, which applies them after blending.

**Tech Stack:** Rust 2021, wgpu 30 (WebGPU on wasm32, Metal natively), WGSL validated by naga 30, wasm-pack, headless Chrome via `chrome-devtools-axi`, Tweakpane 4 (CDN) on the example page.

## Decisions This Plan Makes (the spec left them to the builder)

- **Preset.** iryoku's High settings (threshold 0.1, local contrast factor 2.0, corner rounding 25 %) with two changes:
  - the orthogonal search reaches 16 px each way (`SmaaEffect::REACH`), half of High's 32 (High's 16 steps cover 2 px each; Medium's 8 steps reach 16);
  - there is no diagonal search (High has 8 diagonal steps).

  The single pass's apron fixes its reach. The three-pass reference's reach is `SmaaOptions::three_pass_reach`, 1-64, default 16. The quality cost against reach 32 is measured in Task 7.
- **Tile.** The tile is 16 x 16 output pixels, and one workgroup of 16 x 16 invocations serves it. The apron is two arms. The horizontal arm covers luma columns −18..34 by rows −4..18 relative to the tile origin, which gives edges over −16..33 by −2..17. The vertical arm is the transpose. Together they cover every read that the 17 x 17 weights block makes: the tile plus the ring to its right and below that the blend reads.
- **Edge-free tiles exit early.** Phase 1 finds the edges of the 17 x 17 block from a 20 x 20 luma block. A tile with none writes its input (plus film, from Task 6) and returns. Only the other tiles load the arms.
- **Area texture.** Embed the 1x subtexture of iryoku's `Textures/AreaTex.h`: its first 80 rows, RG8, 160 x 80, 25,600 bytes. They are stored as `smaa_area.bin` and loaded with `include_bytes!` into an `Rg8Unorm` texture.
- **No search texture.** It only decodes iryoku's bilinear two-texel fetches. These passes read exact edge flags instead, from the edges texture or from workgroup memory, so they don't need it. Say so in the module docs.
- **Vignette stays in the tonemapper.** The spec lists the vignette with grain and dither. But `tonemap.wgsl` applies it to scene-linear light before the tone curve (`scene = lens * (p.exposure * vignetteMask(uv) * local)`), so no later pass can apply it and still match the tonemapper's image. It is also smooth, like chromatic aberration, so SMAA never sees it as an edge. Only grain and dither are deferred. Tell the owner (PR text).
- **Film plumbing is explicit.** `ToneMapOptions::defer_film` leaves grain and dither to a later pass. Each frame, the app calls `smaa.set_film(tonemap.later_film())`, the way `BloomEffect::exposure` takes the tonemapper's exposure today. The volume stays generic.
- **Bench and gate.** The example's bench cycles SMAA, SMAA three-pass and TAA:
  - 4 rounds, each mode for 8 s per round (a 4 s settle, then a 4 s profile window), after a 3 s warm-up;
  - the drawing buffer at 1920 x 1080;
  - scene time held fixed, so every mode draws the same frame.

  "Cheaper" means a lower mean AA time than the other mode, and lower in at least 3 of the 4 paired rounds. The AA time is the sum of `exclusive_ms` over the mode's labels: `SMAA` (single pass); `SMAA/Edges`, `SMAA/Weights` and `SMAA/Blend` (three-pass); `TAA/Resolve` (TAA).

## Review Focus

1. **Frame sizes that are not a multiple of the 16 px tile, and tiny frames.** Partial tiles, and aprons clamped at the image's border, must give the same image as the three passes, with nothing unwritten. Task 2 `single_pass_matches_three_pass` at 250 x 190 and 7 x 5.
2. **Edge runs longer than the reach, and edges that run into the frame's border.** They must stay finite and give equal results in both modes, and a straight axis-aligned edge must stay sharp. Task 1 `straight_axis_aligned_edges_stay_sharp`; Task 2's test images include a slope of 1/40.
3. **A signal that isn't sRGB-encoded** (`encode_srgb: false`, native sRGB surfaces). Edges must be found on the encoded luma, and blending must happen in linear light. Task 2 `single_pass_matches_three_pass` (linear variant); Task 6 `deferred_film_matches_the_tonemapper_s` (linear variant).
4. **Resizes and mode switches at runtime** (window drags, the bench switching modes). No stale intermediate textures. Task 2 `resizing_and_switching_modes_match_fresh_effects`.
5. **Grain disappearing in a mode where SMAA doesn't run while the tonemapper defers.** The example derives `defer_film` from its mode every frame. Task 7 step "grain shows in every mode".

- [ ] **Step 4: Write `smaa_common.wgsl`**

Port iryoku's `SMAA.hlsl` (MIT; read it at <https://github.com/iryoku/smaa/blob/master/SMAA.hlsl>): `SMAALumaEdgeDetectionPS` (Rec. 709 luma, threshold, local contrast adaptation), `SMAAArea`, `SMAADetectHorizontalCornerPattern`, `SMAADetectVerticalCornerPattern`, the orthogonal part of `SMAABlendingWeightCalculationPS` and `SMAANeighborhoodBlendingPS`. Give the WGSL file a header saying so, and point to `smaa.rs` for the licence. Where iryoku reads two texels with one bilinear fetch, read the two flags and mix them. The searches walk one pixel at a time, as follows:

```text
horizontal (p = (x, y) has a top edge); cross(c) = left(c, y) or left(c, y - 1):
  l = x; while l > x - reach and !cross(l) and top(l - 1, y): l -= 1
  r = x; while r < x + reach and !cross(r + 1) and top(r + 1, y): r += 1
  d = (x - l, r - x); e1 = 0.75 left(l, y) + 0.25 left(l, y - 1); e2 = the same at column r + 1
  weights.rg = area(sqrt(d), e1, e2), then the corner factors from left(l, y + 1), left(r + 1, y + 1),
               left(l, y - 2), left(r + 1, y - 2) (iryoku's int2 offsets)
vertical (p has a left edge): the same with x and y swapped and top and left swapped -> weights.ba
area texel = 16 * round(4 * (e1, e2)) + sqrt(d); uv = (texel + 0.5) / (160, 80); textureSampleLevel(..).rg
```

Implement the rest of iryoku's logic as he writes it:
- **Luma** is computed on the sRGB-encoded signal. If flag 1 is clear, encode the input first.
- **Blending** decodes the two texels to linear light when the input is encoded, mixes them, then encodes the result again. This is what iryoku's sRGB reads do. A pixel whose four weights sum below 1e-5 returns `smaaColorAt(p)` untouched.

- [ ] **Step 5: Write `smaa_passes.wgsl` and `smaa.rs`**

`smaa_passes.wgsl` holds three entry points, `edges`, `weights` and `blend`, with `@workgroup_size(8, 8)`. Its accessors read the input, the edges texture and the weights texture with `textureLoad`. Each pass writes every pixel:
- **edges:** each pixel stores `smaaDetectEdges` into the edges texture.
- **weights:** a pixel with no edge stores zero and returns, which stands in for iryoku's stencil. Every other pixel stores `smaaWeights(p, i32(params.reach))`.
- **blend:** stores `smaaBlend` into the output. Weights outside the frame count as 0.

Build the pipelines with `layout: None` and `get_bind_group_layout(0)`, as `ToneMapEffect`'s local exposure does. In `smaa.rs`, use the `distance_fog.rs` and `taa.rs` structure:
